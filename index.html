Behind the scroll

One gesture, one chapter.

This page answers a common brief: an Apple-style image-sequence hero that feels smooth on a Mac trackpad but stutters on a Windows mouse wheel in Chrome. The fix is not more smoothing. It is treating scroll as intent, and keeping decoding off the critical path.

Input normalized per device

Pixel deltas from Chrome, line deltas from Firefox, trackpad inertia and touch drags are reduced to one direction. A pause, a reversal or a fresh swipe starts a new gesture; inertia tails are ignored. One click or one swipe moves exactly one chapter.

Fixed-time transitions

Each chapter change is a GSAP tween of the frame index with a fixed duration and easing, so playback speed no longer depends on whether the visitor has a 120 Hz trackpad or a notched mouse.

Bounded decode window

Frames download as compressed WebP and are decoded with createImageBitmap only around the current chapter. Memory stays flat instead of holding hundreds of full-size bitmaps, which is what crashes iOS Safari.

Sized for the screen

Landscape screens load a 1440×810 sequence; portrait phones load a lighter, re-composed 640×1136 sequence. The canvas never allocates more pixels than the frames contain, which matters on 150% scaled Windows laptops.

Smooth scroll where it helps

The hero owns input while it is on screen. After the last chapter it hands control to Lenis, and ScrollTrigger drives the reveals here. Scroll back to the top and the hero picks up at its last chapter.

Measurable on real devices

Open ?debug for a live overlay with FPS, requested and drawn frame, decoded cache size and the detected input type.
